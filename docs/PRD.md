# PRD — 청년정책지원 챗봇 Backend

## 뭘 만드는지

온통청년 API의 정책 데이터를 RAG로 검색해 주거·일자리·교육·복지문화 4개 분야에 맞춤 답변을 제공하는 FastAPI + LangGraph 기반 챗봇 백엔드.

## 핵심 기능 (MVP 완료됨 — 유지보수/리팩토링 대상)

1. **도메인별 정책 RAG 답변** — 4개 전담 에이전트(housing/employment/education/welfare)가 PGVector에서 분야별 정책을 검색해 한국어 답변 생성
2. **LangGraph Multi-Agent 오케스트레이션** — `analysis`(의도 분석) → 도메인 fan-out(`{domain}_search → {domain}`) → `composer`(fan-in, 최종 답변 조립)
3. **후속질문 맥락 처리** — `contextualize` 노드가 후속질문을 독립형 질의로 재작성, 직전 턴 정책 메모리(`policy_memory`)로 "두 번째 정책" 같은 참조 해소
4. **정책 상세 조회 + 자격진단 + D-day** — 마감일 기반 D-day 계산, 로그인 사용자 대상 소득·학력 조건 기반 자격진단
5. **정책 데이터 수집 + 임베딩** — 온통청년 오픈 API → httpx 수집 → 청킹 → PGVector 저장
6. **회원가입 · 로그인** — 회원/게스트 판별, `AsyncPostgresSaver` 전환 기준
7. **스트리밍 답변 출력** — `astream` + `StreamingResponse`

## 이 하네스가 다루는 범위 (MVP 제외 사항)

- **새 도메인/기능 추가는 대상이 아니다.** 이 하네스는 신규 기능 개발이 아니라 **기존 코드베이스의 구조 개선(리팩토링)**을 목표로 도입되었다.
- 프론트엔드는 별도 레포([rag-doc-chatbot-frontend](https://github.com/Minji6/rag-doc-chatbot-frontend))이므로 다루지 않는다.
- 인프라/배포(Docker, CI/CD)는 이 문서의 범위 밖이다.
- 각 리팩토링 phase는 **동작을 바꾸지 않는다** — 응답 결과, API 스펙, DB 스키마가 리팩토링 전후로 동일해야 한다. 동작 변경이 필요한 버그 수정은 별도 phase로 명시적으로 분리한다.

## 페르소나 기준 (참고용 프롬프트 프레임)

phases/step 설계 시 상황에 맞는 페르소나를 택해 프롬프트에 반영한다:

- **코드베이스 이해와 리팩토링** — 구조 문제/중복 코드/성능 병목/유지보수 위험을 식별하고 기능은 그대로 둔 채 품질만 개선. 이 프로젝트의 기본 렌즈.
- **클린 아키텍처 재구성** — 책임 분리, 모듈성 향상, 결합도 감소가 필요한 phase에 사용.
- **다중 에이전트 워크플로우(아키텍트/엔지니어/리뷰어/옵티마이저)** — 이미 harness 자체의 설계(A~D)→실행(E)→리뷰(`/review`) 흐름이 이 구조에 대응하므로 별도 도입 불필요.
