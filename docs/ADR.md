# ADR — 청년정책지원 챗봇 Backend

형식: 뭘 선택했는지 / 왜 선택했는지 / 뭘 포기했는지.

## ADR-001: LangGraph 기반 Multi-Agent 오케스트레이션

- **선택**: 단일 거대 프롬프트 대신 `analysis → fan-out(도메인별 search+agent) → composer` 구조의 StateGraph.
- **이유**: 도메인별 정책 검색/응답 로직을 독립적으로 테스트·수정 가능하게 분리하기 위함. 여러 도메인이 동시에 해당되는 질문(예: "일자리랑 주거 정책 같이 알려줘")도 병렬 fan-out으로 처리 가능.
- **포기한 것**: 단일 에이전트 대비 그래프 구성/디버깅 복잡도가 늘어남. 각 도메인 노드가 독립적으로 LLM을 호출하므로 지연시간·비용이 단일 호출보다 높음.

## ADR-002: PostgreSQL + pgvector (RAG 저장소)

- **선택**: 별도 벡터 DB(Pinecone 등) 대신 기존 PostgreSQL에 pgvector 확장.
- **이유**: 회원/대화 이력 데이터와 정책 벡터 데이터를 하나의 DB로 관리해 운영 복잡도를 낮춤.
- **포기한 것**: 전용 벡터 DB 대비 초대규모 벡터 검색 성능 최적화(ANN 인덱스 튜닝 옵션)는 제한적.

## ADR-003: 게스트/회원 이력 저장 이원화

- **선택**: 게스트는 `InMemorySaver`, 로그인 회원은 `AsyncPostgresSaver`로 대화 이력 저장소를 분리.
- **이유**: 게스트 세션까지 DB에 영구 저장할 필요가 없어 비용·용량을 절감.
- **포기한 것**: 게스트가 로그인 전환 시 기존 대화 이력을 이어받는 기능은 없음(별도 마이그레이션 로직 필요).

## ADR-004 (하네스 도입): 이 리팩토링 작업에 harness_framework 적용

- **선택**: `scripts/execute.py` 기반 phase 순차 자동 실행 하네스를 채택. 신규 기능 개발이 아니라 **기존 코드 리팩토링** 목적으로 한정.
- **이유**: 리팩토링 작업을 작은 phase 단위로 쪼개 각 phase가 "기능 불변 + 품질 개선"이라는 동일한 AC를 갖도록 강제하기 위함. `CLAUDE.md`/`docs/*.md`가 매 phase 프롬프트에 가드레일로 주입되어, 세션이 바뀌어도 아키텍처 경계(fan-out/fan-in 구조, controller-service 분리 등)를 벗어나지 않도록 함.
- **포기한 것**: `execute.py`는 `claude -p --dangerously-skip-permissions`로 각 phase를 무인 실행하며 자동 커밋한다. 사람의 실시간 검토 없이 코드가 바뀌고 커밋될 수 있다는 리스크를 감수하는 대신 처리 속도를 얻음 — 이 트레이드오프가 부담되면 phase 실행 후 리뷰를 거쳐 수동 커밋하도록 `execute.py`를 수정해 사용한다.
